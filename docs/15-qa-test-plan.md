# 15 — خطة اختبار نظام جدار الأسئلة الحية (Live Q&A Wall)

**الملف**: `docs/15-qa-test-plan.md`
**النطاق**: اختبار منظومة جدار الأسئلة الحية (المراحل أ–هـ) — الأنواع العامة (ائتمان) والإدارية، الواجهات الثلاث، والأمان/الأداء.
**الطريقة**: اختبار آلي خفيف (`scripts/qa-smoke.mjs`) + اختبار API يدوي عبر curl + اختبار واجهة في المتصفح.

> **ملاحظة أمان مهمة (سلوك البيئات):** نقاط الجمهور العامة محمية بـ **Turnstile + Rate limit**. هذه الحمايات تعمل بنمط **Fail-Open محلياً** و**Fail-Closed في الإنتاج**:
> - **بالنسبة للاختبار الكامل** (بما فيه الـ 200 الناجحة لنقاط الجمهور) اعمل ببيئة dev **دون** `TURNSTILE_SECRET_KEY` و`UPSTASH_*` (أو أزلها مؤقتاً للاختبار الفردي ثم أعدها — النهج المستخدم للتحقق أدناه).
> - **للتحقق من الحماية فعلياً (403)**: أضف المفاتيح أو اعمل بالإنتاج بنسخة مؤقتة.

---

## 1. التحقق الآلي الخفيف — `scripts/qa-smoke.mjs`

سكربت Node واحد (`fetch`) يغيّر المسار الكامل ويطبع `✓ PASS` / `✗ FAIL` مع عدّاد ختامي ورمز خروج (`0` نجاح / `1` فشل) صالح لـ CI.

```bash
node scripts/qa-smoke.mjs --base=http://localhost:3000 --user=admin --pass='...' \
  [--dir=store-test]          # اختياري: اسم مجلد عزل البيانات (افتراضياً يستعمل إعداد السيرفر)
```

المتغيرات مقبولة أيضاً عبر `QA_USER`/`QA_PASS`/`QA_BASE`.

**شروط التشغيل:**
- خادم `next dev` يعمل، و`ADMIN_USER`/`ADMIN_PASS` صحيحان (مستخدم `admin` المبذور من `ADMIN_PASSWORD`).
- لحصول فحص كامل (تشمل الـ `200` للانضمام/السؤال/التصويت) يجب أن تكون **Turnstile معطلة** في بيئة التشغيل؛ وإلا تُرفض النقاط العامة بـ 403/400 (سلوك مقصود، فراجع §2 للعزل).

**يغطي 20 فحصاً:**
| # | ما يفحصه |
|---|---|
| 0 | تسجيل دخول إداري يعيد `token` |
| 1 | إنشاء جلسة |
| 2 | تفعيل الجلسة (فتح الأسئلة) |
| 3 | `session/current`: جلسة نشطة بلا أسئلة |
| 4 | تسجيل حضور |
| 5 | إرسال سؤال → `pending` |
| 6 | السؤال غير مرئي قبل الموافقة |
| 7 | موافقة المشرف |
| 8 | السؤال مرئي بعد الموافقة |
| 9 | إنشاء استفتاء |
| 10 | بدء الاستفتاء |
| 11 | تسجيل تصويت → `tallies[1]=1` |
| 12 | منع التصويت المزدوج → `409` |
| 13 | إيقاف الاستفتاء |
| 14 | نتائج الاستفتاء ظاهرة (showResults + totalVotes) |
| 15 | رفض سؤال يخفيه عن العام |
| 16 | سؤال قصير جداً → `400` |
| 17 | تعقيم HTML (`&lt;script&gt;`) |
| 18 | نقطة إدارية دون `token` → `401` |
| 19 | `Origin` غير مسموح → `403` |

**التنظيف الذاتي:** يحذف الاستفتاء والجلسة (وسجل أصواتهما) بعد التشغيل عبر الواجهات الإدارية، فيبقى المخزون نظيفاً.

> التحقق الحالي: **20/20 PASS** بنسخة dev بعد عزل Turnstile/Upstash مؤقتاً وإعادة `.env.local` كما كان.

## 2. تجهيز بيئة اختبار معزولة (لا تلوّث الإنتاج/المخزون الافتراضي)

1. انسخ `.env.local` احتياطياً (مثال `.env.local.bak`).
2. أنشئ نسخة مؤقتة دون أسطر `TURNSTILE_SECRET_KEY=` و`UPSTASH_REDIS_*=` (انظر §1 "ملاحظة أمان").
3. شغّل خادماً منفصلاً على منفذ حر مع عزل البيانات:
   ```bash
   $env:QA_DATA_DIR="C:\tmp\qa-store-test"; $env:PORT="3100"; npm run dev
   ```
4. نفّذ السكربت (§1) على `--base=http://localhost:3100`.
5. بعد الانتهاء: أوقف الخادم وأعِد `.env.local` الأصلي من النسخة الاحتياطية وتحقق من تطابق البايتات.

## 3. مصفوفة اختبار API عبر curl

### 3.1 الحصول على رمز إداري (JWT)

```bash
curl -s -X POST http://localhost:3000/api/admin/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"YourAdminPassword"}' \
  | jq -r .token
```
استخدم الرمز كـ `$TOKEN` في أوامر الإدارة أدناه.

### 3.2 المسار السعيد (Happy Path) — لكل أمر النتيجة المتوقعة

| # | الأمر | النتيجة |
|---|---|---|
| 1 | `POST /api/qa/admin/session` `{action:"create",title:"S1"}` | `200` + `result.id` جديد |
| 2 | `POST /api/qa/admin/session` `{action:"activate",sessionId}` | `200` + `active:true` |
| 3 | `GET /api/qa/session/current` | `active:true`، `questions:[]`، `acceptingQuestions:true` |
| 4 | `POST /api/qa/attendee/join` `{name:"ضيف1"}` | `200` + `attendeeId` |
| 5 | `POST /api/qa/attendee/join` (نفس الاسم) | لا تكرار في `attendeeNames` |
| 6 | `POST /api/qa/question` `{attendeeId,name,text}` | `201` + `status:"pending"` |
| 7 | `POST /api/qa/admin/moderate` `{action:"approve",sessionId,questionId}` | `200` + `status:"approved"` |
| 8 | `GET /api/qa/session/current` | السؤال المعتمد يظهر في `questions` |
| 9 | `POST /api/qa/admin/poll` `{action:"create",sessionId,prompt,options:[3]}` | `200` + `result.id` |
| 10 | `POST /api/qa/admin/poll` `{action:"start",...,pollId}` | `200` + `active:true` |
| 11 | `POST /api/qa/poll/vote` `{attendeeId,pollId,optionIndex:1}` | `200` + `tallies[1]=1` |
| 12 | نفس التصويت من نفس `attendeeId` | `409 already-voted` |
| 13 | `POST /api/qa/admin/poll` `{action:"stop",...,pollId}` | `200` + `showResults:true` |
| 14 | `GET /api/qa/session/current` | نتائج الاستفتاء ظاهرة |
| 15 | `POST /api/qa/admin/moderate` `{action:"reject",...}` | السؤال يختفي من العام |

### 3.3 قيود الصياغة (Validation — كلها توقّع `400`)

| الحالة | النقطة |
|---|---|
| `text` أقل من 2 حرف | `/api/qa/question` |
| `text` أكثر من 300 حرف | `/api/qa/question` |
| `name` أكثر من 60 حرف | `/api/qa/attendee/join` |
| `options` < 2 أو > 6 | `/api/qa/admin/poll` |
| `prompt` فارغ عند الإنشاء | `/api/qa/admin/poll` |
| `action` غير معروف | `/api/qa/admin/session` |
| JSON مكسور (`-d 'broken'`) | أي نقطة POST → `400 Invalid JSON body` |

### 3.4 المصادقة والصلاحيات (توقّع `401` / `403` / `503`)

| الحالة | النقطة | النتيجة |
|---|---|---|
| بلا `Authorization` | أي `/api/qa/admin/*` | `401` |
| `Bearer` منتهي/مزوّر | أي `/api/qa/admin/*` | `401` |
| بلا `ADMIN_PASSWORD`/Users (إنتاج) | `/api/qa/admin/*` | `503` |
| **دور `viewer`** | `moderate`، `poll`، **`session`** | `403` (الثلاثة تفرض الآن `role==='admin'`) |
| `Origin: https://evil.example.com` | كل النقاط | `403 Forbidden: origin not allowed` |

### 3.5 التعقيم

- أرسل `text:"<script>alert(1)</script>"` ثم اعتمدها → في `session/current` ولوحة الإدارة تظهر `&lt;script&gt;alert(1)&lt;/script&gt;` (لا تُنفّذ).

### 3.6 Rate limit (في الإنتاج مع Upstash)

- تكرار عام سريع على أي نقطة جمهور → `429` بعد/حسب النافذة (5/10د لكل IP لكل نقطة).
- `admin-api` → `429` بعد 100/10د في الإنتاج.

### 3.7 الاتساق وسينات الحالة

- `delete` جلسة → تُحذف أسئلتها وصناديقها **وسجل أصواتها** (`mutateBoth`).
- `delete` استفتاء → حذفه واصواته.
- `activate` جلسة أخرى → السابقة تتوقف (`acceptingQuestions:false`) وتختفي من العام.
- بلا جلسة نشطة: `join`/`question`/`vote` → `409 no-active-session`.
- جلسة مغلقة (`acceptingQuestions:false`): `question` → `409 not-accepting`.

## 4. اختبار الواجهة (يدوي في المتصفح)

### 4.1 صفحة الجمهور `/en/live` و`/ar/live`
- بوابة التسجيل تعمل وتحفظ الجلسة في `sessionStorage` (إعادة تحميل = «مرحباً بعودتك»).
- إرسال سؤال → رسالة «تم الاستلام»، ويظهر للجمهور فقط بعد موافقة المشرف.
- استفتاء نشط: التصويت يحدَّث فوراً، والزر يُعطَّل بعد التصويت (لا تكرار).
- اتجاهية RTL/LTR صحيحة، والترجمات كاملة بلا مفاتيح فارغة.

### 4.2 شاشة العرض `/en/live/screen`
- وضع «استعدوا» بلا جلسة نشطة.
- الأسئلة المعتمدة تدور تلقائياً (كل 7 ثوانٍ).
- عند إيقاف استفتاء/إظهار النتائج تظهر أشرطة النتائج المباشرة.
- ملء الشاشة + عدّاد الحاضرين.

### 4.3 لوحة الإدارة `/en/admin/live`
- تسجيل الدخول مشترك مع لوحة الطلبات (نفس `token`).
- إنشاء/تفعيل/حذف جلسة، موافقة/رفض/تمييز سؤال، إنشاء/بدء/إيقاف/عرض نتائج/حذف استفتاء.
- الاستطلاع الدوري (5 ثوانٍ) يحدّث القوائم لحظياً.
- حساب `viewer` لا يستطيع إدارة (محظور `403`).

## 5. الحالات القصوى والتزامن

- **تزامن تصويت**: عدة طلبات متوازية لنفس `attendeeId`/`pollId` → صوت واحد يُسجَّل (بفضل القفل + `mutateBoth`).
- **سلامة الملف**: انقطاع أثناء الكتابة → الملفان `qa-data.json`/`qa-votes.json` سليمان (كتابة ذرّية `rename`)، ولا `.tmp` عالقة.
- **بيانات قديمة/ناقصة**: ملف JSON يدوي بلا حقول → `readQaData`/`normalizeData` يعيدان بنية صالحة بلا انهيار.

## 6. محاكاة يوم الفعالية (اختبار القبول النهائي)

مسار زمني كامل يضمن نهاية سلسة:
1. قبل الحدث: لوحة ← إنشاء جلسة «جلسة 1» + تفعيل → شاشة تعرض وضعاً نشطاً.
2. الجمهور يسجّل حضوراً ويطرح أسئلة؛ المشرف يوافق/يفلتر؛ استفتاء يُبدأ ويُصوّت ويُعرض.
3. الانتقال لجلسة 2: إنشاء + تفعيل (تُوقَف السابقة تلقائياً).
4. الإنهاء: حذف/إنهاء الجلسات → عودة الشاشة لوضع «استعدوا».
5. تحقق: لا أخطاء في `console`، وتزامُن بين الجهات < ~5 ثوانٍ.
