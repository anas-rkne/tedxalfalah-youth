## 1. تغيير تاريخ الحدث ومكانه

### 1.1 المكان الصحيح الرئيسي — Sanity (للعميل) ✅

**المهمة للعميل — دقيقة واحدة:**

1. ادخل **Sanity Studio**: `https://tedxalfalahyouth.sanity.studio`
2. من القائمة الجانبية انقر **Event Info** ثم افتح **الوثيقة الوحيدة** (لا تنشئ نسخة ثانية أبدًا).
3. غيّر:
   - **Event Date** (حقل `date` — بصيغة `YYYY-MM-DD` مثل `2026-12-19`)
   - **Venue** (حقل `venue`)
4. انقر **Publish** (زر أزرق أعلى الشاشة).

**ماذا يحدث بعدها؟** الـ Webhook يعيد بناء الصفحة الرئيسية تلقائيًا خلال دقيقة — التاريخ والمكان يُحدَّثان في **بيانات JSON-LD** (بيانات منظمة تظهرها جوجل في نتائج البحث — `eventSchema` في `src/app/[locale]/page.tsx:34-40`).

### 1.2 🚨 النقطة المهمة — هناك تاريخان يظهران!

**الموقع يعرض التاريخ في شاشتين من مصدرين مختلفين — يجب تحديث كليهما:**

| أين يظهر | مصدره | من يغيّره |
|---|---|---|
| بيانات جوجل/النتائج (JSON-LD) | **Sanity** — حقل `eventInfo.date` | العميل (الخطوات أعلاه) |
| **نص الصفحة الرئيسية** (Hero تحت "Save the Date:") | **ملفات الترجمة** — `messages/en.json:66` (`home.hero.date`) و`messages/ar.json:66` (`home.hero.venue` السطر 67) | **المطور** — تعديل نصي عبر Git |

**خطوات تطويرية بديلة إن أراد العميل تغيير النص الظاهر فورًا:** يمكن للمطور مؤقتًا إظهار تاريخ الـ Sanity في Hero (قرار تقني — يُطلب من المطور تنفيذه في `Hero`/`layout`)، لكن الوضع الحالي: **النص المرئي من ملفات الترجمة** و**تاريخ المحركات من Sanity**.

> **تنبيه للعميل:** عند تغيير موعد الحدث، اطلب من المطور تحديث **الملفين معًا** (Sanity + الترجمة على السطرين أعلاه) وإلا ظهر تاريخ قديم في الصفحة الرئيسية رغم تحديث بيانات المحركات.

## 2. إظهار/إخفاء أقسام الرئيسية: المتحدثون والرعاة والفريق (دقيقة واحدة — بلا كود)

**المهمة للعميل:**

1. ادخل Sanity Studio → **Event Info** → الوثيقة الوحيدة.
2. ستجد **ثلاثة حقول أزرار (ON/OFF)** — كلها لأقسام **الصفحة الرئيسية فقط**:
   - **Show Speakers Section (Homepage)** (`showSpeakers`) — قسم «Speakers» بالرئيسية.
   - **Show Sponsors Section (Homepage)** (`showSponsors`) — شريط الرعاة (`SponsorsStrip`).
   - **Show Team Section (Homepage)** (`showTeam`) — قسم «Meet the Team» بالرئيسية.
3. فعّل (ON) للإظهار أو عطّل (OFF) للإخفاء الكامل.
4. **Publish**.

> **قرار العميل 2026-08-13**: صفحات `/speakers` و`/team` **لا تتأثر بهذه الأزرار إطلاقًا** — تفتح دائمًا وتعرض «قريبًا» حتى يُنشر محتوى (`isPublished: ON`). الأزرار تتحكم بقسم الرئيسية فقط.

**متى تستخدمها؟** قبل الإعلان الرسمي عن المتحدثين (الموقع نظيف بلا أسماء)؛ وعند قلة الرعاة المؤكدين. المحتوى لا يُحذف — فقط يتوارى.

## 3. إضافة محتوى جديد (خطوات مرقمة — للعميل)

> القاعدة الذهبية في كل نوع: **الحقل `Published` (isPublished) مغلق افتراضيًا عمدًا — لتظهر عنصرك يجب تفعيله قبل Publish**. وإلغاء تفعيله لاحقًا = إخفاء فوري بلا حذف.

### 🎤 إضافة متحدث (Speaker)
1. القائمة الجانبية → **Speaker** → `+ New Speaker`.
2. املأ: **Full Name** (إجباري)، **Photo** (إجباري — اضبط الـ hotspot)، Short Descriptor، Talk Title، Bio (100–150 كلمة)، روابط التواصل، و**Announcement Wave** (رقم الترتيب: 1 = يظهر أولًا).
3. فعّل **Published: ON**.
4. **Publish** → يظهر في صفحة `/speakers` وقسم المتحدثين بالرئيسية خلال دقيقة (عبر Webhook).

### 🗓️ إضافة جلسة (Session)
1. **Session** → `+ New Session`.
2. املأ: **Title** (إجباري)، **Type** (`Talk`/`Break`/`Activation`/`Registration`)، **Start/End Time** بصيغة 24 ساعة `HH:MM` (مثل `09:15`)، و**Location**.
3. لفقرات Talk: اربط المتحدث من حقل **Speaker** (اختر من القائمة المنبثقة — يظهر اسمه في الجدول تلقائيًا).
4. فعّل **Published: ON** → **Publish** → تظهر في صفحة `/schedule` (تُرتب حسب وقت البدء).

### 🎪 إضافة نشاط (Activation)
1. **Activation** → `+ New Activation`.
2. املأ: **Name** (إجباري)، **Image** (إجباري)، **Description** (50–80 كلمة — إجباري)، **Location in Venue**، و**Display Order** (رقم ترتيب العرض).
3. **Published: ON** → **Publish** → تظهر في صفحة `/activations`.

### 🤝 إضافة راعٍ (Sponsor)
1. **Sponsor** → `+ New Sponsor`.
2. املأ: **Name** (إجباري)، **Logo** (إجباري)، **Tier** (Platinum / Gold / Silver / Community / Supporter)، **Website URL** (اختياري — يُفتح عند الضغط على الشعار).
3. **Published: ON** → **Publish**.
4. **(شرط أولا)**: يجب أن يكون `showSponsors` مفعّلًا في Event Info (القسم 2) ليرى الزوار القسم.
5. **ملاحظة صادقة**: الرعاة يظهرون في **شريط الرعاة بالصفحة الرئيسية فقط** — لا توجد صفحة `/sponsors` حاليًا في الموقع.

## 5. تمديد موعد التقديم ⏰ (المطور فقط)

**المسار الحرفي:** `src/lib/constants.ts:1` — الثابت `APPLICATION_DEADLINE` (صفحة apply تستورده في `src/app/[locale]/apply/page.tsx:10` وتفحصه في السطر 29 — موعد الإغلاق **يُحسب على الخادم**، لا يمكن للمتصفح تلاعبه).

**الخطوات (مهمة المطور):**
1. افتح `src/lib/constants.ts`.
2. عدّل قيمة السطر الأول — الصيغة الإلزامية:
   ```
   "YYYY-MM-DDTHH:MM:SS+04:00"   // بتوقيت الإمارات (UTC+4) صراحةً
   ```
   مثال: ليغلق في 15 أكتوبر منتصف الليل → `"2026-10-15T23:59:59+04:00"`.
3. احفظ + ارفع إلى GitHub (القسم 7) — أو إعادة نشر يدوية في Hostinger.
4. **(اختياري معرض مطابق)**: عدّل أيضًا النص الظاهر في بانر الرئيسية إن لزم — `src/components/home/ApplyBanner.tsx:5` (يقرأ `NEXT_PUBLIC_APPLICATION_DEADLINE` ثم الافتراضي "September 14, 2026").

> **تنبيه:** تمديد الموعد **يتم عبر الكود فقط** — لا يوجد أي إعداد له في Sanity، ولا يستطيع العميل تغييره من اللوحات.
> **سلوك الإغلاق**: بعد الموعد تختفي الفورمات ويظهر نص "التقديم مغلق" (مفتاحا `page.apply.closed.title/body`) — ويعاود الظهور تلقائيًا إن مددت الموعد.

## 6. تغيير رابط التذاكر

**المسار الحرفي:** متغير `NEXT_PUBLIC_PLATINUMLIST_URL` (القالب في `.env.local.example:13`). **حاليًا صفحة `/tickets` مخفية (تعيد 404 بطلب العميل) ولا يوجد زر شراء ظاهر يستخدم المتغير** — يبقى جاهزًا للاستخدام فور إعادة تفعيل الصفحة.

**الخطوات (المطور أو مسؤول اللوحة):**
1. لوحة Hostinger → Web Apps → التطبيق → **Environment Variables** (أو ملف `.env` في جذر المشروع).
2. عدّل `NEXT_PUBLIC_PLATINUMLIST_URL` بالرابط الجديد من منصة Platinumlist.
3. **أعد البناء (Deploy/Rebuild) وليس مجرد Restart** — لأنه `NEXT_PUBLIC_` (يُدمج في حزمة المتصفح وقت البناء).
4. عند إعادة تفعيل صفحة `/tickets` لاحقًا، جرّب منها: زر التذاكر يفتح الرابط الجديد.

> **لا تأثير جانبي**: هذا الرابط هو وجهة زر الشراء فقط — لا يمس الفورمات أو البريد أو أي نظام آخر.

## 7. تحديث الموقع عمومًا (Git Push → إعادة بناء)

الموقع يستضاف على **Hostinger Node.js** والمستودع مرتبط بـ GitHub (عبر Web App).

### دورة التحديث (مهمة المطور):
1. المطور يعدّل الكود محليًا (نصوص/تصميم/إصلاحات).
2. يرفع إلى GitHub: `git add .` ثم `git commit -m "..."` ثم `git push`.
3. **Hostinger يسحب التغييرات**: تلقائيًا (إن كان **Auto-deploy** مفعّلًا في إعدادات Web App) أو يدويًا بضغط زر **Deploy** في لوحة التطبيق.
4. تعاد عملية البناء (`npm run build` — من `package.json:7`) ثم التشغيل (`npm start` — سطر 8). أي فشل بناء يُظهر في **Build Logs** دون إيقاف النسخة القديمة (يمرّرها Hostinger كحماية) — راجع `docs/08` §2.

### ✅ قائمة تحقق للمشرف بعد كل تحديث:
- [ ] **Build Logs** خالية من أخطاء حمراء (في لوحة Web App → Logs).
- [ ] الصفحة الرئيسية والـ `/apply` تعملان بلا خطأ 500/404 غير مقصود.
- [ ] سلوك الفورمات سليم (أرسل رسالة Contact تجريبية — راجع `docs/10` §3.3 إن لم تصل).
- [ ] المحتوى الجديد المعروض (متحدث/جلسة) يظهر باللغتين.
- [ ] `https://` يعمل والشهادة صالحة (راجع `docs/08` §4 بند 1).

> **تنبيه:** أي تغيير في الإنتاج يستلزم **اختبار النموذجين** (Apply + Contact) بعد التحديث مباشرة — الفورمات هي المسار الأكثر تأثرًا بأي تغيير في `next.config`/المتغيرات.
