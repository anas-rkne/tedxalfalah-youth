## 1. نبذة عامة عن المشروع

تطمح فعالية **TEDxAlFalah Youth** إلى خلق تفاعل حي وذاكري ومباشر بين جمهور الفعالية وبين ما يُعرض على المسرح. لتحقيق ذلك، يُقدَّم هذا المقترح لبناء نظام **«جدار الأسئلة الحية»** (Live Q&A Wall) — وهو نظام رقمي متكامل يتيح للحاضرين المشاركة عبر هواتفهم الذكية المزودة بكاميرات، ويُعرض ناتج التفاعل بشكل حيًّ وصريح على شاشة عرض كبيرة داخل قاعة الفعالية.

يهدف النظام إلى رفع مستوى مشاركة الجمهور وتحويل الحضور من «مستمع سلبي» إلى «مشارك نشط»، وفق أعلى المعايير المتبعة في فعاليات TEDx العالمية والعالمية.

### ما الذي يجعل هذا النظام مميزًا؟

- يعمل **ضمن الموقع الرسمي** للفعالية — بلا أي أدوات خارجية أو وسيطة.
- يدعم **نوعين من التفاعل**:
  1. **أسئلة مفتوحة** يكتبها الجمهور ويُعرض على الشاشة أسئلة معتمدة.
  2. **استفتاءات اختيارية (Multiple Choice)** يتم التصويت عليها بنتائج حية تظهر لحظيًا.
- **شاشة عرض منفصلة** للجمهور (وضع ملء الشاشة — تُعرض على البروجيكتور).
- **لوحة إدارة** خاصة بالفريق لمراقبة ومصادقة وتوجيه كل ما يصل قبل ظهوره على الشاشة.
- دعم كامل للغتين **العربية (RTL)** و**الإنجليزية (LTR)**.

## 2. أهداف المشروع

| الهدف | الوصف |
|-------|-------|
| **تفاعل حي** | إشراك الجمهور في الأسئلة والاستفتاءات خلال الفعالية وبالوقت الفعلي |
| **سهولة المشاركة** | مشاركة من أي هاتف عبر مسح QR أو رابط قصير — بلا تطبيقات |
| **رقابة كاملة** | موافقة المشرف قبل ظهور أي محتوى على الشاشة (منع المحتوى غير اللائق) |
| **نتائج لحظية** | عرض نتائج الاستفتاءات في لحظة إغلاق التصويت |
| **ثنائية اللغة** | تجربة عربية وإنجليزية متكاملة |
| **استقرار واستمرارية** | عمل موثوق على السيرفر الحالي دون بنية معقّدة إضافية |

## 3. المتطلبات الوظيفية

تنقسم متطلبات النظام إلى خمس مجموعات وظيفية رئيسية، كل منها مرتبط بجمهور مخصص:

### 3.1 مجموعة الجمهور (الحضور عبر الهاتف)

- [x] تسجيل حضور خفيف وسريع (إدخال الاسم أو رمز اختياري) — مرة واحدة تكفي لجلسة كاملة.
- [x] عرض الجلسة النشطة حاليًا (اسم المقطع أو مقدم الفعالية).
- [x] كتابة **سؤال مفتوح** نصي يرسل إلى المشرف ليُعرض بعد الموافقة.
- [x] المشاركة في **استفتاء اختياري** بالاختيار من عدة إجابات.
- [x] رؤية **نتائج الاستفتاء** لحظة فتح النتائج.
- [x] إمكانية التبديل بين **العربية والإنجليزية** أثناء المشاركة.
- [x] منع الغش: حصر التصويت (صوت واحد لكل مشارك لكل استفتاء).

### 3.2 مجموعة الشاشة (عرض المسرح / البروجيكتور)

- [x] وضع **ملء الشاشة** (Kiosk / Fullscreen) بدون أي أزرار تحكّم ظاهرة.
- [x] عرض **الأسئلة المعتمدة** فقط، بخط كبير وواضح ومريح للقراءة من مسافة بعيدة.
- [x] عرض **نتائج الاستفتاءات الحية** بشكل مرئي (أشرطة تقدم / نسب مئوية) لحظة فتحها.
- [x] الانتقال التلقائي بين الشاشات بالتموج بحالة الجلسة (سؤال مفتوح / استفتاء / انتظار).
- [x] دعم كامل للعرض العربي (RTL) والإنجليزي (LTR).

### 3.3 مجموعة الإدارة (فريق الفعالية)

- [x] **بدء / إنهاء** جلسة أسئلة، وفتح / إغلاق استقبال الأسئلة.
- [x] **مراجعة الأسئلة** المقدمة: موافقة / حجب / تمييز كمميز.
- [x] **إنشاء / تعديل / إيقاف / عرض** نتائج الاستفتاءات الاختيارية.
- [x] عرض عدّادات حية: عدد الحاضرين، عدد الأسئلة، عدد الأصوات.
- [x] الدخول الآمن عبر نظام اللوحة الإدارية الحالية (نفس بيانات مشرفي الموقع).

### 3.4 مجموعة التقنية (متطلبات النظام)

- [x] التخزين على **ملف JSON مستمر** على السيرفر (سريع للكتابة المتكررة).
- [x] **قفل كتابة** لمنع تلف الملف عند تزامن عدة عمليات كتابة في نفس اللحظة.
- [x] المزامنة الحية عبر **Polling** (استطلاع دوري) — متوافق تمامًا مع بيئة الاستضافة الحالية.
- [x] **حماية من الإغراق**: تحديد عدد الطلبات لكل عنوان IP.
- [x] **حماية من الروبوتات (Bots)**: التحقق عبر Cloudflare Turnstile.
- [x] **تنقية المحتوى**: تعقيم النصوص (مكافحة حقن الأكواد XSS).
- [x] **النسخ الاحتياطي**: إمكانية تصدير البيانات بعد الفعالية إلى ملف.

### 3.5 مجموعة إدارة الجلسات

- [x] إمكانية إنشاء **عدة جلسات** (مثال: جلسة أسئلة بعد كل متحدث رئيسي).
- [x] تحديد أي جلسة **نشطة** حاليًا يُعرض منها الأسئلة والاستفتاءات.
- [x] تخزين أرشيف الجلسات السابقة داخل النظام.

## 4. السيناريو التشغيلي

هذا هو الوصف التفصيلي لسير الفعالية من منظور الفريق والجمهور بالخطوات الفعلية:

### قبل بدء الفعالية (التهيئة)

1. يدخل **مشرف الفريق** إلى لوحة الإدارة.
2. ينشئ جلسات الأسئلة وفق برنامج الفعالية (مثلًا: «حوار — المتحدث الأول»).
3. يُنشئ الاستفتاءات الاختيارية المخطط لها مسبقًا (نصوص الأدوات وخياراتها).
4. الجهات تُجهّز **رمز QR / رابط المشاركة** وتُعرض على شاشة كبيرة أو تُطبع وتُعلّق في القاعة.

### أثناء الفعالية (التشغيل)

1. الحاضرون **يمسحون رمز QR** أو يفتحون الرابط على هواتفهم.
2. يسجلون حضورًا خفيفًا (الاسم / رمز اختياري) مرة واحدة.
3. على المسرح، يبدأ المشرف **جلسة الأسئلة** ويفتح باب الاستقبال.
4. الحضور يكتبون أسئلتهم نصيًّا أو يشاركون في الاستفتاء النشط.
5. **المشرف يستعرض الأسئلة الواردة** ويوافق على الملائم لعرضه على الشاشة.
6. **شاشة المسرح** تعرض تلقائيًا الأسئلة المعتمدة أو نتائج الاستفتاء الحيّة.
7. عند انتهاء المقطع، يغلق المشرف استقبال الأسئلة أو ينتقل لجلسة جديدة.

### بعد الفعالية (الإغلاق)

1. يغلق المشرف جميع الجلسات.
2. تُصدَّر البيانات (الأسئلة، الأصوات، الحضور) إلى ملف لمراجعتها أو أرشفتها.

## 5. المعمارية التقنية

يُبنى النظام ضمن المشروع الحالي (Next.js 16 + TypeScript + Tailwind) ويستفيد من كل البنية التحتية الموجودة (المصادقة، الحماية، الترجمة، الاستضافة).

### مخطط عام

```
┌─────────────────────┐    ┌───────────────────┐    ┌──────────────────────┐
│   هواتف الجمهور     │    │   شاشة المسرح     │    │   لوحة إدارة الفريق  │
│   (تسجيل + أسئلة    │    │   (عرض سؤال /     │    │   (موافقة + تصويت +  │
│    + تصويت)         │    │    نتيجة استفتاء) │    │    إدارة الاستفتاءات)│
└─────────┬───────────┘    └─────────┬─────────┘    └──────────┬───────────┘
          │       الرابط / QR       │                         │
          └────────────┬────────────┴─────────────────────────┘
                       ▼
        ┌─────────────────────────────────────────────┐
        │       Routes API (Next.js Backend)           │
        │   /api/qa/*  +  استطلاعات دورية              │
        └──────────────────────┬──────────────────────┘
                               ▼
                   ┌──────────────────────────┐
                   │   store/qa-data.json     │
                   │   (ملف بيانات مستمر)     │
                   └──────────────────────────┘
```

### التقنيات المستخدمة

| المكوّن | التقنية |
|---------|---------|
| إطار العمل | **Next.js 16** (المشروع الحالي) |
| اللغة | **TypeScript** |
| التنسيق | **Tailwind CSS** |
| الأيقونات | **lucide-react** |
| التحقق من المُدخلات | **Zod** |
| الترجمة | **next-intl** (عربي/إنجليزي) |
| المصادقة (لوحة الإدارة) | **JWT + scrypt** (اللوحة الحالية) |
| التخزين | **ملف JSON** + قفل كتابة |
| الحماية | **Upstash Rate Limit + Cloudflare Turnstile** |
| الاستضافة | VPS الحالي عبر **PM2** |

## 6. الصفحات والمَسارات الجديدة

يُضاف إلى الموقع ثلاث صفحات رئيسية جديدة:

| الصفحة | الرابط | الجمهور | الغرض |
|--------|--------|---------|-------|
| **صفحة المشاركة** | `/live` | الجمهور (هواتفهم) | تسجيل حضور + كتابة سؤال + تصويت |
| **شاشة العرض** | `/live/screen` | شاشة المسرح | عرض الأسئلة المعتمدة والنتائج الحية |
| **لوحة الإدارة** | `/admin/live` | فريق الفعالية | موافقة + تحكّم + إدارة استفتاءات |

### ملاحظات على المسارات

- جميع المسارات تُسبق بمعرّف اللغة: مثال `en/live` و`ar/live` (نفس نظام الموقع الحالي).
- صفحة المشاركة ولوحة الإدارة **غير** مفهرسة لمحركات البحث.
- يمكن توفير **رابط قصير** لها لتسهيل كتابته يدويًا أو تحويله لرمز QR.

## 7. واجهات برمجة التطبيقات (API)

تُنفَّذ مجموعة من نقاط النهاية (Endpoints) خلف بادئة `/api/qa/`:

### نقاط نهاية عامة (تُستخدم من هواتف الجمهور والشاشة)

| الطريقة | المسار | الوظيفة | الحماية |
|---------|--------|---------|---------|
| **GET** | `/api/qa/session/current` | جلب بيانات الجلسة النشطة (الأسئلة المعتمدة + نتائج استفتاءات) | عام (قراءة) + Rate Limit |
| **POST** | `/api/qa/attendee/join` | تسجيل حضور خفيف | Rate Limit + Turnstile |
| **POST** | `/api/qa/question` | إرسال سؤال مفتوح | Rate Limit + Turnstile |
| **POST** | `/api/qa/poll/vote` | تسجيل تصويت على استفتاء | Rate Limit + Turnstile |

### نقاط نهاية مُدارة (تُستخدم من لوحة الإدارة فقط)

| الطريقة | المسار | الوظيفة | الحماية |
|---------|--------|---------|---------|
| **GET** | `/api/qa/admin/questions` | استعراض كل الأسئلة بكل الحالات | admin (JWT) |
| **POST** | `/api/qa/admin/session` | بدء / إنهاء / تبديل جلسة | admin (JWT) |
| **POST** | `/api/qa/admin/moderate` | موافقة / حجب / تمييز سؤال | admin (JWT) |
| **POST** | `/api/qa/admin/poll` | إنشاء / إيقاف / عرض نتيجة استفتاء | admin (JWT) |

### معايير الأمان على كل نقاط النهاية

- **التحقق من الأصل (Origin)** في كل الطلبات لمنع الطلبات من مواقع خارجية.
- **محدد المعدل (Rate Limit)** لكل عنوان IP (لمنع الإغراق الآلي).
- **تحديد حجم الإدخال** (حد أقصى لعدد الأحرف في كل حقل).
- **تنقية النصوص** قبل حفظها أو عرضها.

## 9. المزامنة الحية

بما أن بيئة الاستضافة الحالية (VPS + PM2) لا تتضمن بنية WebSocket، فإن المزامنة الحية تُنفَّذ عبر **آلية الاستطلاع الدوري (Polling)** — وهي نفس الآلية المستخدمة حاليًا في لوحة الإدارة الموجودة (تحديث كل 15 ثانية) لكن بفترات أقصر للحساسية الزمنية:

| العميل | فترة الاستطلاع | البيانات المُستطلَعة |
|--------|---------------|----------------------|
| **شاشة العرض** | كل 3 ثوانٍ | الأسئلة المعتمدة + نتائج الاستفتاءات |
| **لوحة الإدارة** | كل 3 ثوانٍ | كل الأسئلة (بما فيها المعلّقة بانتظار الموافقة) |
| **صفحة الجمهور** | كل 4 ثوانٍ | نتائج الاستفتاءات وقائمة الجلسات |

### لماذا الـ Polling وليس WebSocket؟

- **التوافق:** يعمل بسلاسة مع البنية الحالية و PM2 و reverse-proxy دون إعدادات إضافية.
- **البساطة:** لا يحتاج خادم اتصالات خاصة أو صيانة اتصالات طويلة.
- **الأداء الكافي:** عدد الحضور محدود (حدود فعالية)، والفترات المقترحة تعطي استجابة فورية تقريبًا.
- **قابلية التحسين:** يمكن لاحقًا الترقية إلى **Server-Sent Events (SSE)** أو WebSocket إن أُريدت حسمية كاملة — يُناقش في «النطاق خارج الوثيقة».

## 10. الأمان والحماية

### طبقات الحماية المطبّقة

| الطبقة | الإجراء |
|--------|---------|
| **مكافحة الإغراق** | تحديد عدد الطلبات لكل عنوان IP عبر Upstash Rate Limit على كل نقاط النهاية العامة |
| **مكافحة الروبوتات** | التحقق عبر Cloudflare Turnstile على صفحة المشاركة (يمنع إرسال البوتات للأسئلة والأصوات) |
| **تنقية المحتوى** | تعقيم كل النصوص (إزالة أي أكواد HTML/JS ضارة — مكافحة XSS) قبل العرض |
| **المصادقة** | لوحة الإدارة محمية بنظام JWT + تجزئة كلمات المرور (نفس اللوحة الحالية) |
| **التحقق من الأصل** | رفض أي طلب من ضيوف/مواقع خارجية عبر التحقق من Origin |
| **حد الإدخال** | الحد الأقصى لطول السؤال والإجابات، وعدد الأصوات لكل مشارك |
| **القراءة/الكتابة** | قفل الكتابة على ملف البيانات لمنع تلفه |
| **الملفات** | التحقق من مسارات آمنة وعدم تعريض ملف البيانات للعموم |

### سياسة محتوى الشاشة

- لا يُعرض على الشاشة سوى الأسئلة التي **وافق عليها المشرف** (الحالة `approved`).
- الأسئلة تصل بحالة «معلّقة» (pending) → يقرر المشرف.
- يمكن للمشرف **حجب** (rejected) أي سؤال أو تمييزه **كمميز** (featured) لعرضه بتمييز خاص.

## 11. دعم اللغتين

- يُضاف في ملفات الترجمات (`en.json` و `ar.json`) مساحات ترجمة جديدة تحت اسم `qa` (أو `page.live`).

- تُخزَّن النصوص الإدارية (عناوين الجلسات، نصوص الاستفتاءات) بإصدارين عربي وإنجليزي اختياريًا.

## 12. تجربة المستخدم (سير العمل الكامل)

### 12.1 من منظور الحاضر

1. **مسح رمز QR / فتح الرابط** على الهاتف.
2. **تسجيل حضور خفيف**: إدخال الاسم (أو رمز اختياري) — بلا بريد إلكتروني أو كلمة مرور.
3. تظهر الشاشة الرئيسية، وتعرض **الجلسة النشطة** الحالية.
4. يمكن للحاضر:
   - كتابة **سؤال مفتوح** في حقل نصي والضغط «إرسال».
   - المشاركة في **استفتاء** بالضغط على الخيار المفضل (يظهر تقدم النتائج بعد فتحها).
5. إشعار «تم الاستلام» بعد إرسال السؤال مع تنبيه أن العرض يخضع لموافقة المشرف.

### 12.2 من منظور فريق الإدارة

1. **تسجيل الدخول** إلى لوحة الإدارة (نفس بيانات الموقع).
2. الدخول إلى قسم «الأسئلة الحية».
3. **إنشاء / اختيار الجلسة النشطة** وفتح باب الاستقبال.
4. مراجعة قائمة الأسئلة الجديدة و**الموافقة / الحجب** بنقرة واحدة.
5. إنشاء الاستفتاءات وتعيين خياراتها، وفتح التصويت ثم فتح النتائج.
6. متابعة العدّادات الحية (عدد الحضور، عدد الأسئلة، عدد الأصوات).

### 12.3 من منظور شاشة المسرح

1. تفتح الصفحة على جهاز متصل بالبروجيكتور وبوضع ملء الشاشة.
2. تنتقل تلقائيًا حسب حالة الجلسة:
   - عند فتح استفتاء: تعرض التقدّم الحي للنتائج.
   - عند وجود أسئلة معتمدة: تعرضها بشكل تلقّافي ودوري.
   - عند عدم وجود محتوى نشط: تعرض شاشة «انتظار» أنيقة باسم الفعالية.

## 13. خطة التنفيذ

يُنفَّذ المشروع **على مراحل متتالية** لضمان الجودة والتحكم بالمخاطر. تتضمن كل مرحلة اختبارًا قبل الانتقال إلى التالية.

### المرحلة (أ) — الأساس والبنية التخزينية
- (`نطاق`) وحدات التخزين والقفل وملف البيانات الأولي والتحقق من المُدخلات.
- (`تسليم`) القدرة على قراءة وكتابة البيانات بأمان، وإنشاء/بدء جلسات.
- (`اختبار`) التحقق من سلامة كتابة/قراءة ملف البيانات دون تلف عند التزامن.

### المرحلة (ب) — مشاركة الجمهور والاستفتاءات
- (`نطاق`) نقاط نهاية تسجيل الحضور وإرسال الأسئلة والتصويت، وصفحة المشاركة.
- (`تسليم`) تجربة مشاركة كاملة من الهاتف: تسجيل + سؤال + تصويت + رؤية النتائج.
- (`اختبار`) تحقق تفاعلي محلي من ثلاث هواتف/نوافذ ومزامنة النتائج.

### المرحلة (ج) — لوحة الإدارة
- (`نطاق`) نقاط نهاية الإدارة الموافقة/الحجب والاستفتاءات، وصفحة لوحة الإدارة.
- (`تسليم`) تحكم كامل للفريق في الجلسات والأسئلة والاستفتاءات بأمان.
- (`اختبار`) سير كامل: جمهور يرسل → مشرف يوافق → يظهر على الشاشة.

### المرحلة (د) — شاشة العرض والتكامل
- (`نطاق`) صفحة الشاشة، رمز QR / رابط قصير، إكمال الترجمة.
- (`تسليم`) عرض المسرح الكامل + رابط مشاركة قابل للمسح.
- (`اختبار`) تشغيل الشاشة وصفحة الجمهور معًا ومحاكاة الفعالية.

### المرحلة (هـ) — الأمان والنشر والتوثيق
- (`نطاق`) تحصين نهائي (Rate Limit، Turnstile، sanitize، قيود)، رفع على السيرفر، توثيق.
- (`تسليم`) نسخة إنتاج مستقرة + دليل تشغيل للفريق + خطوات النشر.
- (`اختبار`) اختبار شامل على الاستضافة الفعلية بعد النشر.

## 14. متطلبات النشر

عند الإنتاج تُنفَّذ الخطوات التالية على السيرفر (VPS) عبر PM2:

1. رفع الكود إلى المستودع (Git).
2. على السيرفر: `git pull` → `npm install` → `npm run build`.
3. نسخ متغيرات البيئة: `cp .env.local .next/standalone/.env.local`.
4. إعادة تشغيل الخدمة: `pm2 restart <app>`.

### نقطة حرجة — استمرارية البيانات

- يجب حفظ ملف بيانات الجدار (`store/qa-data.json`) في **مسار مطلق ثابت** خارج مجلد `.next/` الذي يُعاد بناؤه في كل مرة.
- وإلا ستفقد بيانات الجلسات في كل عملية `build` — وهذا أهم نقطة نشر لهذه الخاصية.
- يُضبط ذلك عبر تعريف مسار ثابت في إعدادات النشر و PM2 (دليل العمل `cwd`).

## 15. الاختبار والتحقق من الجودة

### أنواع الاختبارات المطبّقة

- **اختبار الوحدات**: التحقق من دوال التخزين والقفل والتحقق من المدخلات.
- **اختبار نقاط النهاية (API)**: عبر السجلات (كل `GET/POST` يعيد الاستجابة الصحيحة والرموز السليمة).
- **اختبار التكامل**: سير كامل من الإرسال حتى العرض على الشاشة.
- **اختبار الحماية**: محاولات إغراق (Rate Limit)، حقن (XSS)، طلبات من مصادر خارجية.
- **اختبار ثنائي اللغة**: التحقق من العرض والإدخال في العربية والإنجليزية.
- **اختبار النشر**: تثبيت على الاستضافة الفعلية والتأكد من بقاء البيانات بعد إعادة التشغيل.

### معايير القبول (الجاهزية)

- يرسل الحاضر سؤالًا كاملًا ويعمل التصويت والنتائج الحية دون أخطاء.
- يوافق المشرف ويحجب الأسئلة بسهولة ويرى المحتوى على الشاشة فورًا.
- يُعرض كل شيء بشكل سليم بالعربية والإنجليزية.
- يبقى ملف البيانات سليمًا بعد إعادة تشغيل السيرفر.

## 17. نطاق خارج الوثيقة (اختيارات مستقبلية)

هذه ميزات **غير** مشمولة في النسخة الأولى، وقد تُنفّذ لاحقًا عند الحاجة:

- **الترقية إلى لحظية مطلقة**: استبدال الـ Polling بـ **Server-Sent Events (SSE)** أو **WebSocket** لعرض لحظي بلا تأخير.

- **استغلال قاعدة بيانات علائقية** (مثل PostgreSQL) لنطاقات أكبر وجمهور أوسع.
- **صوّت للأسئلة**: السماح للحاضرين بالتصويت لرفع الأسئلة الأكثر طلبًا إلى أعلى القائمة.
- **تصدير تقارير تفاعلية مفصلة** بعد الفعالية إلى ملف PDF أو Excel.
- **وضع «متحدث ضيف»**: إتاحة تسجيل دخول خاص للمتحدثين لاستقبال أسئلة مخصصة لهم.
